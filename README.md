# 笔顺订正工作台（Flask + Canvas）

学生写出字形后，老师用尽量少的动作示范如何订正**笔顺**。在米字格画布上对着范字临摹，
系统按原始书写方向计算离散 Fréchet 距离来配笔，求出最少的 **移笔 / 删笔 / 补笔** 动作序列，
可逐步播放、可一键采纳“下一步移笔/删笔”并按实际笔序重算；支持标记必须保留的笔，
保留要求无法满足时给出“无解”。

## 用 Docker Compose 启动

```bash
docker compose up --build
```

然后打开：

- <http://localhost:8000>
- 或 <http://localhost:5000>（Compose 额外把宿主 5000 映射到容器 8000，兼容 Flask 默认端口习惯）

镜像用 gunicorn 跑 `app.server:app`，带 `/healthz` 健康检查。

## 本地直接运行

```bash
pip install -r requirements.txt
python run.py                 # 默认 0.0.0.0:8000，可用 PORT 覆盖
# 打开 http://127.0.0.1:8000
```

## 使用流程

1. 顶部选择范字（内置 **一 十 人 八 大 口 土 木**，均附标准笔序，见 `app/data/characters/`）。
2. 在米字格中按住拖动书写；最多 10 笔，前端会把每笔精简/等弧长重采样到 **≤64 点**，坐标统一到 **1000×1000 共用网格**。
3. 拖动右上角滑块设定 **离散 Fréchet 上限**（默认 180/1000 网格单位，内置范字与正常临摹的同笔距离约 30–80，异笔通常 ≥260）。
4. 点 **求最优修订**：显示最少动作总数与「移 / 删 / 补」计数，并列出每一步。
5. 用 **播放 / 上一步 / 下一步 / ⏮** 逐步观看：
   - 移笔：蓝色高亮 + `from → to` 标记，笔画顺序徽标重排（几何位置不变，变的是笔序）；
   - 删笔：红色残影提示后移除；
   - 补笔：对应范字笔画以**紫色虚线**（带流动动画）示意；求解后所有缺笔也会先以淡虚线标出。
6. 点 **采纳下一步：删除/移动…**，该动作真正作用于实写笔画，随后前端自动请求，
   **按当前实际笔序重新求解**；右侧记录已采纳动作。可反复采纳直到只剩补笔示范。
7. 每行笔画可勾选 **保留**：保留笔不会被建议删除或移动（行内“删除”按钮也会禁用）。
   若保留笔找不到达标范字笔画，或保留笔的先后顺序与范字笔序冲突，页面直接显示 **无解** 与原因。
8. 笔迹增删、保留项或阈值一变，旧建议立即失效（同步清空、禁用采纳）；若已求过解会自动重算。
9. 没有笔迹时可点 **填入示例笔迹（含典型错误）** 快速体验：示例稳定包含顺序错误、多余笔和缺笔。

### 30 秒演示：播放与采纳

默认范字为“木”，示例稳定给出 **3 个动作（移 1 / 删 1 / 补 1）**：

1. 执行 `docker compose up --build`，打开 <http://localhost:8000>。
2. 点 **填入示例笔迹（含典型错误）**，等待求解；右侧应显示“最少 3 个动作”，
   步骤为删第 4 笔、把第 2 笔移到第 1 位、补范字第 2 笔。
3. 点 **播放**：会依次演示删除残影、移笔高亮/`from → to` 标记和紫色虚线补笔；
   也可用 **⏮ / ◀ / ▶** 单步查看。播完后实写原笔按配笔槽位排好，缺笔保留为虚线。
4. 点 **采纳下一步：删除第 4 笔**：该笔真正从列表删除，页面自动按当前笔序重算，
   最少动作数 `3 → 2`。
5. 再点 **采纳下一步：移动第 2 笔 → 第 1 位**：笔画真正换位并重算，`2 → 1`；
   终态移/删均为 0，只剩 1 个补笔虚线示范，采纳按钮禁用。
6. 勾选任意笔画的 **保留**，旧建议会立即失效并自动重算；保留笔及其所在的不动主干
   不会出现在移/删目标中。若保留笔无匹配或顺序冲突，页面显示中文“无解”。

## 算法说明

### 配笔：按原方向的离散 Fréchet 距离

`app/core/frechet.py` 的 `discrete_frechet(P, Q)` 是标准 O(p·q) 动态规划，
从首点走到末点，**不反转**任何一条曲线，因此撇/捺、逆序笔画不会被当作同向。
只有 `distance ≤ threshold` 的“实写笔 × 范字笔”才进入兼容矩阵。服务端直接对收到的
≤64 点序列计算离散 Fréchet（点数量上限正好把 DP 限制在 64×64）。

### 最少动作：带“不动主干（backbone）”的掩码 DP

范字有 `N` 个笔序槽位，成稿与范字**按笔序一一对应**：每个槽位要么放一笔兼容的实写笔，
要么记一次补笔；没被使用的实写笔记一次删笔。

- 一次“移到任意笔序位置”收费 1。
- 相对顺序与目标槽位一致的若干实写笔可以**不动**，构成递增主干；其余被使用的笔每笔移动一次。
- 对一个确定的配笔方案，最少移笔数 = 使用笔数 − 包含全部保留笔的最长递增子序列长度。

DP（`app/core/planner.py`）按实写当前顺序逐笔处理，状态为
`(最后一条主干槽位 last, 已占用范字槽位掩码 mask)`，每笔三选一：

| 选择 | 代价 | 约束 |
| --- | --- | --- |
| 删除 | 1 | 保留笔禁止 |
| 移动使用 `mv(j)` | 1 | `j` 兼容且未被占用；不约束主干顺序；保留笔禁止 |
| 不动/主干 `bb(j)` | 0 | `j > last`、兼容、未占用 |

结尾对每个未占用槽位加 1 次补笔。`N,K ≤ 10`，掩码仅 `2^10`。
保留笔被强制走 `bb`：既不能删也不能移动；若 DP 无可达终态即 **无解**，
并区分“保留笔无兼容范字笔画”和“保留笔顺序冲突”两种中文原因。

### 可播放步骤与“下一步”

由最优决策先产出删除步，再对剩余笔求“含全部保留笔的最大强制 LIS”作为固定主干，
并把返回的 `backbone` 规范化为这一组实际固定笔，避免不同但等长的 LIS 平局导致
“响应声明不动、步骤却移动它”。随后用确定性的插入构造
`move_operations_to_target`（已用穷举 1..8 全排列 + 随机用例验证：
每次都恰好得到目标顺序、每个移动笔只动一次且无空操作）。移动/删除步的 `from/to/index`
与前端 `applyMove`（先 `splice(from,1)` 再插入结果下标 `to`）严格同一语义；
每个 `index/from` 都是该步执行前的当前笔序下标，因此预览逐步应用与老师采纳完全一致。
每个“下一步”都经性质测试验证：采纳后重新求解的最优值 **恰好下降 1**。
补笔步直接携带范字点列供虚线绘制。

### UID 与混用输入

`strokes[]` 可混用：

- 裸点列：`[[x, y], ...]`；
- 无 `uid` 的笔画对象：`{"points": [[x, y], ...]}`；
- 带任意 JSON 标量 `uid` 的对象，包括数字 UID。

内部始终用请求中的原始下标作为唯一身份；省略的 UID 仅按旧接口习惯在外层响应中
显示为原始下标。因此显式数字 UID 即使和某个裸点列的隐式下标相同，也不会串笔。
步骤中的显式 `uid` 按原值、原类型返回；`backbone` 是原始下标数组，
`backbone_uids` / `unmoved_uids` 是对应的外层 UID 值。

## HTTP API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/` | 画布页面 |
| GET | `/healthz` | 健康检查 |
| GET | `/api/characters` | 范字清单 |
| GET | `/api/characters/<id>` | 某范字完整笔画点列 |
| GET | `/api/sample/<id>` | 确定性错误示例（供“填入示例”/测试） |
| POST | `/api/plan` | 求最优修订 |

`POST /api/plan`：

```json
{
  "character_id": "mu",
  "threshold": 180,
  "strokes": [
    {"uid": "s0", "preserved": false, "points": [[500, 395], "..."]}
  ]
}
```

也可用 `"model": [[[x,y], ...]]` 直接内联范字。返回 `feasible / reason / cost /
counts{move,delete,add} / steps[] / next_action / compatible / dist / assign /
backbone / backbone_uids / fixed_uids` 等。`backbone` 是整套移删步骤都不会指向的原始下标，
`backbone_uids` / `fixed_uids` 是对应的外层 UID 值；它们包含全部 `preserved:true` 的笔画。
超出“≤10 笔 / 每笔≤64 点”等限制时返回 `feasible:false` 与中文原因。


## 已做的实测

- `PYTHONPATH=<deps> python3 -m unittest discover -s tests`：**33/33 通过**，覆盖
  Fréchet 方向性、交换=1 次移笔、多笔/缺笔/多余笔、移删补组合、保留锚定/冲突/无兼容笔无解、
  数量上限、无 UID 倒序、连续删笔下标、数字 UID/裸点列身份碰撞、等长 LIS 平局时
  `backbone` 与步骤一致，以及 120 组随机“下一步必使最优值−1”和 60 组“整段步骤到达终态”性质测试、
  完整 HTTP 采纳重算循环。
- 额外随机自测（最终代码）：
  - **20,000 组**裸点列 / 无 UID 对象 / 显式（含数字、`null`）UID 混用输入，其中 16,900 组有解：
    每步执行前下标有效、被移/删的原始下标不属于 `backbone`、保留笔未被移删、
    播完后剩余笔顺序等于 `assign` 槽位顺序，且每个 `next_action` 采纳重算后代价恰降 1；
  - **300,000 组**合成兼容矩阵 DP 检查，其中 210,997 组有解：
    `cost == moves + deletes + adds`、保留笔均在严格递增主干中。
- 用 **gunicorn `app.server:app`**（即 Docker CMD 的目标）启动后，以 urllib 跑通
  `/healthz`、无 UID 倒序、连续删笔、数字 UID 碰撞，以及 8 个范字的
  “示例 → 求解 → 逐个采纳移/删 → 重算 → 仅剩补笔”循环，每次代价恰降 1；
  保留笔互换返回“无解/顺序冲突”。
- 用 **jsdom + Canvas2D 桩**加载真实页面和运行中的服务（`scripts/dom_smoke.mjs`）：
  范字按钮、默认“木”、示例 cost=3（移1删1补1）、步骤数=3、制造保留冲突出现“无解”、
  取消后恢复 cost=3、两次采纳（删第4笔 → 移第2到第1）后终态移删为0补1、
  单步播放与自动播放到“重播”、保留勾选立即显示失效并自动重算，全程无页面脚本错误。
- 几何口径未改：仍使用 `app/core/frechet.py` 中从首点走到末点、不反转曲线的标准离散
  Fréchet DP。早期版本用 Pillow 渲染核对过范字/虚线位置；本轮主要用上述接口、
  排列不变量和 DOM 冒烟验证。
